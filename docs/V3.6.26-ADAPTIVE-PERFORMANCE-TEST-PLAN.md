# OHLI Social v3.6.26 — Adaptive Performance Test Plan

## What is embedded

`OhliAdaptiveEngine` runs in the Android server process and uses no remote AI API. It maintains an exponentially weighted latency baseline and a small online logistic feedback model with six learned weights. Its inputs are active workers, bounded-queue depth, recent request latency, heap pressure, rejected requests, and a smoothed server-exception rate. It also exports a bounded set of per-route latency samples and caps workers using CPU cores as well as memory class. The controller adjusts the bounded `ThreadPoolExecutor` within a device-memory cap. Its six learned model weights, sample count, and latency baseline are saved to private Android SharedPreferences every 32 training samples and on service shutdown. Route counters and live queue metrics restart fresh; no account data or message content is stored by the optimizer.

The `/health` endpoint is intentionally minimal and public; detailed metrics are served only from authenticated `/api/performance`. Model v2 can safely migrate the earlier v1 weights. The same server path also includes phone/session hash indexes, negotiated GZIP for JSON responses of at least 2 KB, and rename-based JSON backup rotation. Private endpoints remain `no-store`; no account feed, message, notification, or private media response is put in a shared cache.

## Required Android/device validation

1. Build with the checked-in GitHub Actions workflow. Confirm the produced APK includes `OhliAdaptiveEngine.class` and the Android `cloudflared` ABI libraries.
2. On the target low-memory phone, open the server panel and confirm the Adaptive Engine status line is visible. Repeat on a newer device; worker caps should follow memory class.
3. Send normal concurrent requests to `/health`, `/api/me`, feed, chat, Story, and profile endpoints. While signed in, read `performance.mode`, `workerActive`, `workerMax`, `queue`, `learnedLatencyMs`, `failureRatePercent`, and `heapPressurePercent` from `/api/performance`. `/health` exposes only service identity and version.
4. Exercise a burst of simultaneous requests. Confirm bounded queue behavior, no ANR, no out-of-memory termination, and no sustained 503 responses. The engine must reduce concurrency under heap pressure and increase only within the reported cap.
5. Compare JSON endpoints with and without `Accept-Encoding: gzip`. For eligible large responses, verify the compressed response decodes to byte-identical JSON. Small JSON, image/media, and clients without GZIP support must remain valid.
6. Create accounts and sessions, restart the server, sign in again, and verify indexed account/session lookup returns the same users and does not cross account boundaries.
7. Repeatedly send message, like, view marker, story, and profile updates. Stop the app during a write test, restart, and verify the `.tmp`/`.bak` recovery path retains the latest complete valid JSON document.
8. Test on Wi-Fi and mobile-data clients through Cloudflare Tunnel. Record median/p95 latency, data transferred, CPU, heap, battery use, and success rate; compare with v3.6.24 under the same device/network/load.

## Limits

These changes are bounded optimizations for the existing Android-hosted JSON backend. They do not remove the global data lock, convert JSON files into a transactional SQL database, add object storage, provide a TURN/SFU media network, or create an LLM. Do not promise unlimited users, zero lag, or production-grade availability based on static checks alone.
